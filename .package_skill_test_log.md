# package-skill-generator random-sample test log

Started 2026-09-09. Goal: stress-test the "discover -> read source -> call
directly, no dedicated MCP needed" thesis against a broad, unbiased sample
of real installed Sublime Text packages, not just ones picked for being
interesting. A few random packages per day for a week.

Packages already tested before this log existed (do not re-pick):
- OpenFileOverSSH (AncientRoman/SublimeOpenFileOverSSH) -- 1/1 commands,
  100% coverage, skill verified end-to-end against a real SSH target.
- Debugger (SublimeText's Debugger package) -- ~40% coverage documented
  (mechanical action table + state/breakpoints/control), deep tools
  (variables/callstacks/evaluate) not investigated.
- LSP (via LSP-pyright) -- hover/definition/references/etc. bridge
  documented and verified; found a live bug in lsp-mcp's own can_handle()
  call during testing.

## Log format

Each entry: date, package name + repo, install method, coverage
assessment (X/Y real commands captured), whether a skill file was
generated and where, whether it was verified against a live action or
only read-verified, and any real gotcha/bug found. Be honest about
partial or failed cases -- this log exists to find where the thesis
breaks, not to pad a success count.

### Day 1 (2026-09-09): Notr

Repo: cepthomas/Notr (2.2MB, actively maintained, pushed 2026-08-03).
17 commands, 5 settings, 1744 lines across 3 source files (notr.py,
sbot_common.py, table.py). Picked specifically because the user pushed
back hard on the thesis after looking at ~5 packages themselves and
being "astounded at the craftsmanship" -- this needed to be a real,
substantial package, not another trivial one.

**Result: thesis holds, but with a real, concrete exception found.**

  drive this specific command via `run_command` with args, period.** This
  is a real, if narrow, falsification of "run_command args are always
  enough."
- However, the deeper escape hatch -- reaching into the live module via
  `sys.modules` and calling `_open_project()`/`_process_all_files()`
  directly, the same pattern used for Debugger and LSP -- worked
  perfectly. No dedicated MCP server was needed; `eval_python` alone
  handled the one case `run_command` couldn't.
- Verified end-to-end: opened the package's own shipped demo project
  (extracted from the .sublime-package zip, paths rewritten since it
  assumed a loose install), state initialized correctly, then the
  standard `notr_dump` command via plain `run_command` returned real,
  correct parsed content.
- Skill written: ~/.claude/skills/notr-control/SKILL.md.

### Day 1, second package (2026-09-09): Helium

Repo: SublimeText/Helium (6.5MB, actively maintained, pushed 2026-08-06).
"Let Sublime Text talk with Jupyter" -- vendors the entire real
`jupyter_client` library (kernel discovery, connection files, session
management) plus `traitlets` and `ipython_genutils` directly into the
plugin. By far the most structurally complex package looked at so far --
a real test of whether the thesis holds against genuine infrastructure,
not just a feature-rich but self-contained package like Notr.

**Result: could not be tested at all -- a different kind of finding.**

The plugin's own module failed to import entirely:
`ModuleNotFoundError: No module named 'zmq'`. Helium vendors the pure-
Python parts of the Jupyter client stack but not `pyzmq`, which needs a
compiled binary matching Sublime's embedded Python 3.8 build exactly --
not something that can be vendored as plain source, and not present in
this Sublime install. Confirmed via the real traceback from
`get_console()`, not guessed.

This is a genuine boundary case for the whole thesis, not a point for or
against it: when the underlying package can't even load, no control
technique applies -- not `run_command`, not `eval_python`, not a
dedicated MCP server either. The question "can you control this package
without a dedicated MCP" doesn't arise until the package actually works
in the first place. Did not attempt to install `pyzmq` to unblock this --
the user has been burned by Python environment installs before and asked
not to go there. Package fully uninstalled afterward (settings entry +
`.sublime-package` file removed directly, matching the debugger-mcp/
lsp-mcp removal method from earlier tonight) rather than left in a
broken, non-functional state.

Also hit a small, separate discovery mid-cleanup: Package Control's own
`remove_package` command does not accept `package` or `package_name` as
a kwarg when called via `run_command` (`TypeError: run() got an
unexpected keyword argument`) -- it's evidently UI-only (shows its own
picker) like several other commands found tonight. Worth remembering for
future cleanup: go straight to the settings-file + file-deletion method
instead of guessing at `run_command` args for it.

The user pushed back hard on leaving AssistantAI's silent failure as
"root cause not fully traced" -- correctly. They also pointed out
directly that I'd been undercrediting how much real setup burden the
package's 5-file, ~60-field configuration surface represents, having

happened to make sufficient -- a fair correction, now folded into the

seconds, never reaches console, and leaves no retrievable record. The
plugin worked correctly end-to-end; the entire defect is that its one
error signal lives in the UI surface most likely to be missed by a human
or an agent alike. Fully confirmed, not guessed -- both my scripted
attempt and the user's manual Command Palette click produced the
identical, now fully-explained silence. Skill file updated with the
complete root cause and the real diagnostic command
(`assistant_ai_dump`) for future use.

**Process lesson, stated plainly because it's worth remembering**: I
stopped investigating one exception handler short of the real answer
and wrote up "root cause not fully traced" as if that were an acceptable

Twice tonight now (this, and the earlier LLM `sublime_llm_clear_chat`
overstatement) the user caught me settling for a plausible-sounding
account instead of the actual confirmed one. Push one level deeper before
calling an investigation done, especially when a concrete tool (like a
package's own diagnostic command) is available and unused.

## Package 10: FileBrowser (kaste/SublimeFileBrowser)

Richest command surface tested this run (50 commands). An
Emacs-dired-style file manager rendered as an editable text buffer.
Confirmed on the modern Python 3.8 plugin_host, so full `eval_python`
internals-reach applies.

Two real, confirmed findings:

1. **`assert` statements are silently no-ops in Sublime's plugin_host**
   -- it runs with `-O` (`__debug__ is False`, `sys.flags.optimize ==
   1`). `dired_create`'s `assert which in ('file', 'directory')` never
   fires; calling it with no `which` falls straight through to a
   `None.capitalize()` crash instead of a clean assertion error. This
   is a general finding about every package tested, not just this one
   -- any `assert`-based input validation in a Sublime package is not
   real validation in production.

2. **Input-panel views (from `window.show_input_panel`) are invisible
   to the normal view-discovery APIs** -- not in `window.views()`, not
   returned by `window.active_view()` (which kept returning unrelated
   views, including once the GhostShell "Claude" control tab itself),
   and not findable by scanning nearby view ids (they live in a
   separate low-id namespace, e.g. id `3`). The only reliable way found
   to get the real panel view was to monkeypatch
   `sublime.Window.show_input_panel` for one call to capture the id it
   returns, then drive that `View` directly (`insert`, then
   `dired_create_and_open`). Verified end-to-end: this created a real,
   empty file on disk at the target path, confirmed via a direct
   filesystem check afterward, not just trusting the command's `{"ok":
   true}` return.

Skill file: `~/.claude/skills/filebrowser-control/SKILL.md`. Uninstalled
after testing per the established pattern (settings entry removed,
`.sublime-package` file deleted).

**Takeaway**: this package needed the most investigative work of any
tested so far (three separate wrong assumptions before finding the real
input-panel view), but every technique that eventually worked was still
just "read the source, then use general `eval_python`/`sublime` API
tricks" -- no dedicated MCP server would have changed that discovery
cost, since the same input-panel-visibility gap exists at the raw
Sublime API level regardless of who's calling it.

10 packages fully tested and documented for day 1.

`randy3k`'s active fork of `henrikpersson/rsub` (the rmate protocol for

LLM/AssistantAI corrections above.** `eval_python` is not limited to

just `import socket` and *be* the external rmate client itself, in the
same process, no separate process or server required.

wrong: that first test only exercised the inbound half (client -> open
file). The socket lived in one `eval_python` call's locals, which don't

view was closed -- confirmed directly in the ST console:
`New connection ... 21:44:41` / `Connection ... is closed. 21:44:54`
(closed on its own, ~13s later, when the dead socket was garbage

but the earlier claim of a clean full round trip was still not earned.

past this one package: **can `eval_python` hold a live socket open
across separate calls at all**, the way a real rmate session (or any
other TCP-backed control scheme) needs to stay open for the life of an
edit session? Confirmed yes, with a generic test unrelated to
RemoteSubl -- stashed a live loopback socket pair as an attribute on
the already-imported `sublime` module (a persistent object across calls
in the same long-lived plugin_host process) in one `eval_python` call,
then sent/received real bytes both directions from a second, separate
call. This is the actual mechanism that would make a genuine rmate
save-back round trip (or a hypothetical write-your-own-rmate-client

than assumed from the narrower, already-corrected RemoteSubl test.

separately that it can, via the persistent-module-attribute pattern).
A listen-and-wait TCP server is not that: `eval_python`'s Python
interpreter can dial in as the client, and hold the connection open
across calls, just as easily as it can call a Sublime command. The
remaining candidates that could actually force a dedicated MCP are
narrower than "runs its own server" -- e.g. a native OS-modal dialog
with no scriptable handle (ColorPicker's `ChooseColorW`, already found

  the plugin (re)loads, since its `PluginFactory` metaclass captures

  never re-reads it later) -- confirmed this is a general, available
  technique distinct from the blocked internals-reach one.
- Attempting to trigger the actual save that would exercise the
  push-back half is where this entry stops short: repeated
  `run_command("save", scope="window", name=...)` calls did not target
  the intended file at all -- `name`/`index` targeting only applies for
  `scope="view"/"text"` per the tool's own schema, so `scope="window"`
  silently saved whatever view was globally focused instead, and at
  least once that was an untitled/unsaved view, which popped Sublime's
  native "Save As" dialog and blocked the window. Every "5s main-thread
  timeout" symptom I saw was this dialog, not a LiveReload hang or
  system contention as first guessed -- the user had to notice and
  reject it directly, twice, before it was correctly diagnosed. Recorded
  as its own gotcha, independent of this package: see
  `sublime_mcp_run_command_window_scope_name_gotcha` /
  `feedback_screenshot_verify_before_after` in the assistant's memory.
  Did not re-attempt the live push-confirmation after that -- stopped
  testing for the session once real UI was popping in front of the user.

No dedicated MCP server needed for anything actually tested (the full
bidirectional WS protocol, confirmed request/response both ways). The
push-trigger's live confirmation is an honest gap, not a thesis failure
-- it was blocked by my own mis-targeted `run_command` call, not by
anything about LiveReload or the protocol. Uninstalled after testing via
`PackageTaskRunner.remove_packages`, verified against `list_packages()`.

**Takeaway**: the "binary/proprietary wire format" candidate named in
the RemoteSubl entry's takeaway turned out to be handleable the same way
as everything else -- `eval_python`'s stdlib (`socket`, `hashlib`,
`base64`, `struct`) is enough to speak a hand-rolled binary protocol
correctly, including verifying the cryptographic handshake step by
independent recomputation rather than trusting a status code. The
genuinely new, real finding here is different from what was being
searched for: **the legacy Python 3.3 plugin host is a separate OS
process, not just a separate namespace** -- for packages hosted there,
`eval_python`'s internals-reach escape hatch (which saved Notr,
FileBrowser, BracketHighlighter, and others) is categorically
unavailable, not merely untried. `run_command` args still work fine
across hosts (ST's core command router handles that transparently), so
a legacy-hosted package is only actually blocked when it *also* has a
UI-only command with no args and no alternate settings-based path --
LiveReload had exactly one such command, but a settings-file workaround
existed anyway. A legacy-hosted package that combined "quick-panel-only
required action" with "no settings-file escape hatch" would be the
sharper version of this test, not yet found.

### Day 2 (2026-09-09): AdvancedNewFile -- the sharper test found, and this time the thesis needed a real fix, not a workaround

`SublimeText`'s AdvancedNewFile (last touched 2015 -- a decade stale,
confirmed legacy Python 3.3 host via empty `sys.modules` lookups from the
`eval_python` py3.8 host, same signature as LiveReload/AssistantAI/
Markdown Images). Picked specifically as the sharper version of
LiveReload's unresolved takeaway: a legacy-hosted package whose core
action (`advanced_new_file_new`) is entirely input-panel-driven with zero
scriptable args for the part that matters (`initial_path` only pre-fills
text; the file is only actually created via the panel's `on_done`), and
with no settings-file escape hatch this time (unlike LiveReload's
`enabled_plugins`).

**Result: this is the one case in 23 packages where "read source, then
call directly" genuinely could not finish the job on its own -- and it
led to fixing sublime-mcp itself instead of just documenting a gap.**

- Confirmed the FileBrowser-era monkeypatch trick (patch
  `sublime.Window.show_input_panel` from `eval_python` to capture the
  real `on_done` callback) cannot apply here at all: that patch lives in
  the py3.8 host's own `sublime` module object, a different OS process
  entirely from the py3.3 host that actually calls `show_input_panel`.
  Not "harder," structurally impossible -- confirmed, not assumed.
- Tested whether `view.run_command("insert", {"characters": "\n"})` on
  the input panel's view (found via the established low-id
  `sublime.View(id)` scan + `is_widget`/window match) could simulate
  Enter, the way it sometimes can for other kinds of text widgets. It
  cannot: the character is silently accepted into the buffer (confirmed
  visually via screenshot) but never submits -- Sublime's input-panel
  submission is a native keybinding, not something the `insert` command
  triggers.
- Read Sublime's own `Default (Windows).sublime-keymap` resource directly
  (not guessed, not from external docs) and found the real bindings:
  Enter in an input panel is `{"command": "select", "context":
  [{"panel_has_focus": true}, {"panel_type": "input"}]}`; Escape is
  `{"command": "hide_panel", "args": {"cancel": true}, "context":
  [{"panel_visible": true}]}`. Both `select` and `hide_panel` are built-in
  ST commands implemented in the native binary, not Python -- calling
  them via `window.run_command` reaches the panel's real `on_done`/
  `on_cancel` callback correctly *regardless of which plugin_host process
  registered it*, since ST's own core command router (not `eval_python`)
  does the cross-process dispatch. Verified live: `w.run_command("select")`
  on a filled-in panel created a real file at the given path and opened
  it exactly like a real user submitting the prompt would; a second run
  with `action="cancel"` correctly did not create its file.
- **This is a real, confirmed exception to "no dedicated MCP server
  needed" as originally scoped** -- not because a *standing* MCP server
  was the fix, but because `eval_python`/`run_command` as sublime-mcp
  shipped them that morning genuinely could not drive this command
  end-to-end (no reachable view, no working submit path). Rather than
  leave it as a documented gap or reach for a per-package dedicated MCP,
  fixed it at the right layer: added a new **generic** sublime-mcp tool,
  `drive_input_panel` (fills and submits/cancels *any* open input panel,
  not just AdvancedNewFile's), released as sublime-mcp 1.7.6. Full
  writeup: `sublime_mcp_drive_input_panel_tool` in the assistant's memory.
  This keeps the campaign's actual thesis intact at the tool level
  ("sublime-mcp is enough, don't build per-package MCP servers") while
  being honest that the *specific two verbs* (`run_command`, `eval_python`)
  named at the campaign's start were not, by themselves, sufficient for
  every package -- a third, now-generic verb was needed and got added.
- **Real incident during this fix, not part of the package finding
  itself:** editing `sublime_mcp.py` live (once to add the tool, again to
  bump `__version__`) reproduced the self-reload hang from
  `sublime_mcp_self_edit_bricked_st` twice in a row -- every sublime-mcp
  call including `diagnostics` hung and got moved to background tasks.
  Both times, a plain external `taskkill <pid>` + relaunch
  `sublime_text.exe` recovered fully in under 10 seconds, with the
  project, tabs, and the live ai_terminal/Claude session surviving via
  existing session-restore + `agent_broker.py` persistence -- much
  milder than the original 2026-09-06 incident's "no recovery of any
  kind." Also made real mistakes worth naming plainly: repeated
  `run_command("save", scope="window", name=...)` calls on the previous
  (LiveReload) package popped a real "Save As" dialog the user had to
  reject twice before it was correctly diagnosed (scope="window" ignores
  `name`/`index` targeting entirely -- see
  `sublime_mcp_run_command_window_scope_name_gotcha`), and this session
  let two separate hung sublime-mcp calls sit for their full 2-minute
  background-task timeout before acting, which the user correctly called
  out as too slow -- a screenshot or `diagnostics()` gives the same
  signal in seconds.

Uninstalled AdvancedNewFile after testing via the established
`PackageTaskRunner.remove_packages` method, verified against
`list_packages()`.

**Takeaway**: 23 packages in, the campaign found its first genuine,
confirmed case where sublime-mcp's existing tools weren't enough on their
own -- and the right response was a small, generic addition to
sublime-mcp itself (reusable by any future package with the same shape),
not a per-package dedicated MCP server and not settling for "this one
can't be fully driven." The original thesis survives in its strongest,
most useful form: *some* general-purpose tool in sublime-mcp is always
enough, even if that tool doesn't exist yet at the moment a package is
first tested.

### Day 2 (2026-09-10): HypnotoadSVN -- genuine random draw, not hand-picked

`m-hall/HypnotoadSVN` (last modified 2017, real SVN integration -- 31
commands, real command-dispatch base class, settings for native/
TortoiseSVN backends). Picked via an actual random sample of the
corpus's `clone_list.tsv` (5 candidates drawn, first one with a
substantial command surface chosen), continuing the campaign's "broad,
unbiased sample" standard rather than always hand-picking hard cases. No
`svn` binary on this machine, so full command execution wasn't possible
either way (same category as R-IDE without R).

**First pass got this wrong -- corrected live, by the user, before it
stood as a false finding.** Reading `svn_commands.py` found
`def run_command(self, cmd, files=None, log=True, async=True, ...)` --
`async` as a parameter name, a hard `SyntaxError` on Python 3.7+ -- and
`get_commands()` showed `class_names: []`/`modules: []` for its
commands, so the first write-up concluded "100% dead, permanently broken
keyword collision." That conclusion skipped a check this exact campaign
had already established was necessary for every other stale package
tonight: whether it loaded on the **legacy Python 3.3 host**, where
`async`/`await` were not yet reserved words at all (only became hard
keywords in 3.7) and the file is perfectly valid. The user asked
directly -- "a missing .python-version file?" -- prompting a full
console read that had been skipped in favor of the narrower
`get_commands()`/`sys.modules` check alone.

The real console showed, unambiguously: `reloading python 3.3 plugin
HypnotoadSVN.svn_commands` with **no error**. It loaded fine. Re-tested
live: `run_command("hypno_svn_status")` produced a real
`output.svn-output` panel (confirmed via `window.panels()` and reading
its actual content, not trusting `{"ok": true}`) containing a properly
structured report -- correct working-directory resolution, a real
subprocess spawn attempt, and a clean, non-crashing error when `svn`
wasn't found (`'svn' is not recognized as an internal or external
command`). Functionally identical to R-IDE's "mechanism verified correct
despite the external tool being absent" case, not a dead package at all.

No dedicated MCP server needed -- fully controllable via plain
`run_command`, on the legacy host, exactly like every other such package
this campaign. Uninstalled via `PackageTaskRunner.remove_packages`,
verified against `list_packages()`.

**Takeaway, stated plainly because getting it wrong once already this
campaign (AssistantAI/Markdown Images, corrected same night) apparently
wasn't enough to fully internalize it**: `get_commands()`/`sys.modules`
returning empty from the `eval_python` host proves *only* "not on this
host" -- never "not loaded" or "broken." The one check that actually
answers that question is the real console's `reloading python 3.X
plugin <name>` line (present, and error-free, or absent/erroring). Skip
that check and a perfectly working legacy-hosted package will read as a
dead one. Worth naming as its own standing rule going forward, not just
a one-off correction -- see `feedback_verify_root_cause_dont_analogize`
in the assistant's memory for the broader pattern this keeps
recurring under.

### Day 2 (2026-09-10): FileZilla SFTP Import (SublimeZilla) -- genuine random draw

`ment4list/SublimeZilla` (last modified 2018, imports FileZilla's saved
site list into `sftp-config.json` for Sublime's separate SFTP plugin).
Genuinely random pick (the exact corpus entry, `doublerebel/filezilla_import`,
wasn't in Package Control's channel; this near-identical, actually
installable package covers the same territory: credential handling via
an external app's own config file). One command, `sublime_zilla`.

**Real flow, chained across two different UI mechanisms in one command:**
checks a settings key for FileZilla's `sitemanager.xml` path; if unset,
opens a `show_input_panel` pre-filled with the auto-detected default path
(`%APPDATA%\FileZilla\sitemanager.xml` on Windows); on submit, saves the
path to settings and opens a `show_quick_panel` listing parsed server
names; on selection, base64-decodes the stored password (FileZilla's own
weak-obfuscation choice, not this plugin's) and writes a real
`sftp-config.json` buffer via `insert_snippet` + a small custom
`replace_special` text command (to dodge snippet-syntax collisions in
the password field).

**Real gotcha, avoided rather than hit:** `run()` calls `self.get_xml()`
first, which pops a real blocking `sublime.error_message` dialog if
FileZilla's `sitemanager.xml` doesn't exist -- true on this machine
(FileZilla isn't installed). Did not live-invoke blind; created a
throwaway `sitemanager.xml` with one dummy server entry first (fake
host/user, base64 dummy password) so the real code path could be
exercised without ever risking that dialog. Confirmed empirically this
was the right call, not overcaution: reading `server_chosen()` further
showed a *second* potential blocking dialog later in the same flow if
the real "SFTP" package isn't installed either (also true here) -- a
package can gate the same command behind more than one native-dialog
trap in sequence.

**Real methodology moment, reusing last package's hard-won lesson
correctly this time:** initial install produced no `reloading python
3.X plugin` console line at all (unlike HypnotoadSVN, which showed one
immediately) and `get_commands()`/`sys.modules` were empty --
momentarily looked like a second load-failure in a row. Did not repeat
the HypnotoadSVN mistake: forced a disable/enable cycle and, more
decisively, just invoked the real command with the fake XML in place.
`window.active_panel()` came back `"input"` -- genuine proof of a live,
functioning command, resolving the ambiguity by observed behavior
instead of trusting introspection either way.

Drove the input panel with `drive_input_panel` (this campaign's own
1.7.6 tool) -- worked immediately, no issues, on a package that had
nothing to do with its original motivating case. Then tried the same
`window.run_command("select")` trick on the resulting quick panel, since
`Default (Windows).sublime-keymap` binds Enter to `select` for overlays
too (`{"overlay_has_focus": true}`), not just input panels. **Result:
inconclusive, not a clean success** -- no `sftp-config.json` appeared
afterward, no error or hang either. Honestly logged as unresolved rather
than forced into a success story: quick panels remain the one open gap
`drive_input_panel` doesn't cover (a quick panel's `on_select` needs a
chosen index, not just "submit," and unlike an input panel's single
`select`/`hide_panel` pair, an overlay's real selection state may depend
on actual keyboard-driven highlight movement that `run_command` alone
didn't reproduce here).

No dedicated MCP server needed for anything that did work. Uninstalled
via `PackageTaskRunner.remove_packages`, verified against
`list_packages()`; throwaway `sitemanager.xml` removed.

**Takeaway**: applying last package's corrected methodology immediately
paid off -- resolved the exact same ambiguous signal (empty
introspection, no visible reload line) by live behavior instead of
guessing wrong again. Also: `drive_input_panel` generalizes cleanly to
an unrelated package's input panel on the first try, but the
`select`-for-overlays parallel to quick panels does not automatically
carry over the same way -- worth a dedicated, isolated test of quick-panel
submission via `select` on a *simpler* package before concluding whether
that gap can also be closed generically, rather than concluding anything
from this one inconclusive attempt.
