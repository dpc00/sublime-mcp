# package-skill-generator random-sample test log

Started 2026-09-09. Goal: stress-test the "discover -> read source -> call
directly, no dedicated MCP needed" thesis against a broad, unbiased sample
of real installed Sublime Text packages, not just ones picked for being
interesting. A few random packages per day for a week.

**Standing methodology rule (added day 5, applies retroactively to every
entry below that claims "no error occurred"): `get_console(mode="captured")`
is NOT valid for verifying the absence of a crash.** It is explicitly
non-invasive and incomplete -- it can silently drop lines, including
tracebacks, and will falsely report a clean run. It produced exactly this
false negative on SublimeLinter-pyflakes (package #37): a run that had
actually crashed 4/4 times looked crash-free under `mode="captured"` and
only showed the real traceback under `mode="auto"`/`"visible"` (the
complete capture). Any "did this actually work / did this actually
crash" check must use the complete capture, never the incomplete one.
Earlier entries in this log that checked console output for absence of
errors were not necessarily using the complete capture and have not been
retroactively re-verified against this rule -- treat any of them as
provisional if the distinction matters for a specific decision.

**Second standing methodology rule (added closing this campaign, from
the EditorConfig #39 trim-whitespace false finding): an edit-then-save
round trip must verify the edit landed where intended before trusting
the save result.** Inserting a test marker *after* the region actually
being tested (e.g. after trailing whitespace, when testing whether
trailing whitespace gets trimmed) silently changes what the test is
measuring -- the marker makes prior content interior, not trailing, so
there is nothing left for the feature under test to act on. This
produced a real false "bug" report in the same session it was found.
Print/verify the actual buffer content immediately after making a test
edit, before saving and checking the result.

Packages already tested before this log existed (do not re-pick):
- OpenFileOverSSH (AncientRoman/SublimeOpenFileOverSSH) -- 1/1 commands,
  100% coverage, skill verified end-to-end against a real SSH target.
- Debugger (SublimeText's Debugger package) -- ~40% coverage documented
  (mechanical action table + state/breakpoints/control), deep tools
  (variables/callstacks/evaluate) not investigated.
- LSP (via LSP-pyright) -- hover/definition/references/etc. bridge
  documented and verified; found a live bug in lsp-mcp's own can_handle()
  call during testing.

## Log format

Each entry: date, package name + repo, install method, coverage
assessment (X/Y real commands captured), whether a skill file was
generated and where, whether it was verified against a live action or
only read-verified, and any real gotcha/bug found. Be honest about
partial or failed cases -- this log exists to find where the thesis
breaks, not to pad a success count.

## Package 10: FileBrowser (kaste/SublimeFileBrowser)

Richest command surface tested this run (50 commands). An
Emacs-dired-style file manager rendered as an editable text buffer.
Confirmed on the modern Python 3.8 plugin_host, so full `eval_python`
internals-reach applies.

Two real, confirmed findings:

1. **`assert` statements are silently no-ops in Sublime's plugin_host**
   -- it runs with `-O` (`__debug__ is False`, `sys.flags.optimize ==
   1`). `dired_create`'s `assert which in ('file', 'directory')` never
   fires; calling it with no `which` falls straight through to a
   `None.capitalize()` crash instead of a clean assertion error. This
   is a general finding about every package tested, not just this one
   -- any `assert`-based input validation in a Sublime package is not
   real validation in production.

2. **Input-panel views (from `window.show_input_panel`) are invisible
   to the normal view-discovery APIs** -- not in `window.views()`, not
   returned by `window.active_view()` (which kept returning unrelated
   views, including once the GhostShell "Claude" control tab itself),
   and not findable by scanning nearby view ids (they live in a
   separate low-id namespace, e.g. id `3`). The only reliable way found
   to get the real panel view was to monkeypatch
   `sublime.Window.show_input_panel` for one call to capture the id it
   returns, then drive that `View` directly (`insert`, then
   `dired_create_and_open`). Verified end-to-end: this created a real,
   empty file on disk at the target path, confirmed via a direct
   filesystem check afterward, not just trusting the command's `{"ok":
   true}` return.

Skill file: `~/.claude/skills/filebrowser-control/SKILL.md`. Uninstalled
after testing per the established pattern (settings entry removed,
`.sublime-package` file deleted).

**Takeaway**: this package needed the most investigative work of any
tested so far (three separate wrong assumptions before finding the real
input-panel view), but every technique that eventually worked was still
just "read the source, then use general `eval_python`/`sublime` API
tricks" -- no dedicated MCP server would have changed that discovery
cost, since the same input-panel-visibility gap exists at the raw
Sublime API level regardless of who's calling it.

10 packages fully tested and documented for day 1.

`randy3k`'s active fork of `henrikpersson/rsub` (the rmate protocol for
Sublime). Picked specifically because its architecture is the inverse of

caught and corrected before closing this entry, same discipline as the
LLM/AssistantAI corrections above.** `eval_python` is not limited to
Sublime's own API -- it's a full embedded Python interpreter, so it can
just `import socket` and *be* the external rmate client itself, in the
same process, no separate process or server required.

- Opened a raw `socket.create_connection(('localhost', 52698))`,
  received the real banner (`Sublime Text 3 (remote_subl plugin)`).
- Sent a real `open` / `display-name` / `real-path` / `token` / `data: N`

  back via `view.substr()` on the actual opened view.

Initially logged this as a "full real protocol round trip," which was
wrong: that first test only exercised the inbound half (client -> open
file). The socket lived in one `eval_python` call's locals, which don't
survive to the next call, so it was already dead by the time the file's
view was closed -- confirmed directly in the ST console:
`New connection ... 21:44:41` / `Connection ... is closed. 21:44:54`
(closed on its own, ~13s later, when the dead socket was garbage
collected) / `Error closing rmate_test.txt in testhost. 21:45:00` (the

subsequent call kept responding promptly, so the background handler
thread's `cleanup()` (which does call a real `sublime.message_dialog`
on disconnect by default) did not visibly wedge the main thread here --
but the earlier claim of a clean full round trip was still not earned.

Went back and settled the actual crux directly, since it generalizes
past this one package: **can `eval_python` hold a live socket open
across separate calls at all**, the way a real rmate session (or any
other TCP-backed control scheme) needs to stay open for the life of an
edit session? Confirmed yes, with a generic test unrelated to
RemoteSubl -- stashed a live loopback socket pair as an attribute on
the already-imported `sublime` module (a persistent object across calls
in the same long-lived plugin_host process) in one `eval_python` call,
then sent/received real bytes both directions from a second, separate
call. This is the actual mechanism that would make a genuine rmate
save-back round trip (or a hypothetical write-your-own-rmate-client
MCP tool) work via plain `eval_python` -- confirmed generically rather
than assumed from the narrower, already-corrected RemoteSubl test.

`PackageTaskRunner.remove_packages` internals-reach method, verified
against `list_packages()` and against nothing still listening on 52698.

**Takeaway, and the actual point of this entry**: "genuinely needs a
dedicated MCP" would require a client protocol `eval_python` truly
cannot speak -- not just an unusual *direction* of control, and not
just a connection that has to outlive a single tool call (confirmed
separately that it can, via the persistent-module-attribute pattern).
A listen-and-wait TCP server is not that: `eval_python`'s Python
interpreter can dial in as the client, and hold the connection open
across calls, just as easily as it can call a Sublime command. The
remaining candidates that could actually force a dedicated MCP are
narrower than "runs its own server" -- e.g. a native OS-modal dialog
with no scriptable handle (ColorPicker's `ChooseColorW`, already found
and documented above) or a binary/proprietary wire format `eval_python`
has no library for. Both would need testing on their own merits, not

### Isolated follow-up (2026-09-10): resolving the quick-panel `select` gap left open by SublimeZilla

Not a package test -- an isolated mechanism test, as the SublimeZilla entry
itself called for, using a throwaway `window.show_quick_panel` built
straight from `eval_python` (no third-party package involved) to get the
cleanest possible signal.

**Result: the gap is closed, and the answer is narrower than hoped.**

- `run_command("select")` does fire a live quick panel's `on_select`
  callback -- confirmed twice, cleanly: `on_select(0)` fired both times,
  matching the panel's default-highlighted item.
- Read `Default (Windows).sublime-keymap` directly (via
  `sublime.load_resource`, not guessed) for anything bound under an
  `overlay_has_focus` context that could move the highlighted item (the
  equivalent of arrow-key navigation before submitting) -- found nothing.
  Every `overlay_has_focus`-gated binding in the whole keymap is `select`
  itself (Enter) or a `goto`-overlay-specific extend/select variant; there
  is no keymap-reachable, and therefore no `run_command`-reachable, way to
  change *which* item is highlighted before calling `select`.
- **Conclusion**: quick-panel arrow-key navigation is native UI, not a
  Sublime command -- structurally unreachable via `run_command`, the same
  category of gap as ColorPicker's native `ChooseColorW` dialog, just a
  smaller one. `select` alone only ever accepts whatever is *already*
  highlighted (the default item, almost always index 0), never "item N."
  Confirmed authoritatively against Sublime's own official API reference
  (`sublimetext.com/docs/api_reference.html`), not just inferred from the
  keymap's silence: `show_quick_panel()`'s `selected_index` sets only the
  *initial* highlight at open time, and `on_select`/`on_highlight` are
  passive callbacks with no corresponding way to drive the highlight from
  script after the panel is already open -- the keymap search and the
  documented API agree exactly.
- This does **not** reopen the campaign's core finding, because the actual
  fix was already discovered and used earlier this campaign, just not
  named as the general answer to this specific question: the
  `show_quick_panel`-monkeypatch-and-call-the-real-callback-directly
  technique (first used for FileBrowser's input panel, reused successfully
  for BracketHighlighter's `swap_brackets` quick panel) bypasses UI
  navigation entirely and can select any index, not just the default. For
  SublimeZilla specifically, the earlier "inconclusive" `select` attempt
  should have used that technique instead, not `select`.

**Takeaway**: two genuinely different verbs were being conflated under one
question. "Submit whatever's highlighted" (`select`) and "choose a specific
item" (monkeypatch-and-call) are different mechanisms with different
reach -- `select` is not a general quick-panel driver, it's a narrow
accept-the-default action. `drive_input_panel`'s clean generalization to
other packages' input panels does not extend to quick panels, and building
a quick-panel equivalent of `drive_input_panel` would need to select the
monkeypatch approach, not try to extend `select` further.

`core/__init__.py`'s `write_json_file` (called from `persist_requests`,
which every successful request triggers) does an atomic write via
temp-file-then-rename to a `.bkp` backup path. `os.rename()` on POSIX
silently overwrites an existing destination; on Windows it raises
`FileExistsError` instead -- a real, platform-specific bug, not a
one-off. It didn't visibly break the test (the response tab still
rendered correctly, since the exception is in the history-persistence
path, not the request/render path), which is exactly why it went
unnoticed until the console was read in full. Filed:
https://github.com/kylebebak/Requester/issues/41

**Takeaway, reinforcing an existing one**: this is the same lesson as
HypnotoadSVN's misdiagnosis and the WakaTime/PyTest silent-failure
findings -- a component can look like it worked from its visible output
alone while a real, confirmed exception fires in a parallel code path.
Reading the full console after a test, not just checking the one output
that mattered, keeps finding real bugs this campaign would otherwise
report as clean successes.

### Day 3 (2026-09-10): AutoFileName -- first package testing Sublime's autocomplete mechanism (on_query_completions)

`run_command`, but only after three wrong turns, each a genuine
methodology lesson, not a package flaw.**

- First attempt: plain `run_command("auto_complete")` on a bare `<img
  src="` line with no typed prefix -- `is_auto_complete_visible()` false.
  Screenshot confirmed no popup, ruling out an API-reliability doubt.
- Read `get_cur_path()` directly: it returns an empty string unless a

a matched trigger character, a syntactically complete context) are met.

**Takeaway**: this campaign's methodology paid for itself three times in

(it wasn't), don't trust a synthetic test input that a real user's editor

boolean state check with a screenshot when its result contradicts
expectation rather than trusting either blindly.

### Day 5 (2026-09-10): SublimeLinter core (37) -- the async/deferred-worker axis

check) plus SublimeLinter-pyflakes (`last_modified: 2025-04-24`) was the
candidate: pyflakes runs as an async lint worker, not inline.

**Pre-flight dependency, verified not assumed:** the installed
SublimeLinter-pyflakes needs a real `pyflakes` importable by *some*
Python it can subprocess out to; confirmed via `pip show pyflakes` it
was not already present, then `pip install pyflakes` (uninstalled again
at cleanup) -- same "read dependencies before concluding broken"
discipline as TokensCounter's `tiktoken`, applied proactively this time
instead of after a crash.

**Installed via the dedicated `install_package` tool** (not
`run_command install_package`, which threw `TypeError: run() got an

in that command's args, not anything wrong with the plan; switched to
the purpose-built tool and it worked cleanly). SublimeLinter 4.28.2 and
SublimeLinter-pyflakes 1.3.4 both installed successfully per the console.

**Found and fixed a real, live, currently-reproducing bug** in
SublimeLinter's own compatibility shim (`__allo__.py`, nicknamed
"SublimeLinter-lift" in its own log lines): on a *fresh* install of a
linter plugin, its `on_change` handler pessimistically drops a loose
`Packages/<plugin>/.python-version` "lift" file the moment Package
Control's `installed_packages` setting changes, then 5 seconds later
`check_all_plugins()` removes that lift file for real once it sees the
now-installed `.sublime-package` carries its own `.python-version`
(confirmed both declare "3.8", not a version mismatch). But removing the
lift file did not make Sublime re-read the *zip's* internal
`.python-version` on the very next `reload_plugin` -- it fell back to
the legacy default (Python 3.3), and SublimeLinter-pyflakes's `linter.py`
immediately died with `ImportError: No module named 'SublimeLinter'`
(SublimeLinter core itself only exists in the 3.8 host). This is the
same "python-version mismatch across plugin_host processes" failure
category the campaign already named for legacy 3.3-only packages
(AssistantAI, Markdown Images), but here it is triggered transiently, on
a *3.8-declaring* package, by the host's own lift-cleanup shim racing a
`reload_plugin` -- worth a filed issue if this reproduces from a truly
clean profile, not just this heavily-reused test install.

**Fixed without a dedicated MCP, using only what's already
discoverable:** manually recreated the loose
`Packages/SublimeLinter-pyflakes/.python-version` file (content `3.8`)
via `eval_python`, then forced a reload the same way any user would --
`run_command(disable_packages)` / `run_command(enable_packages)`
(plural, per the already-known singular/plural gotcha) -- and confirmed
via `from SublimeLinter.lint import persist; persist.linter_classes`
that `'pyflakes'` was now registered under the 3.8 host with no
traceback. No dedicated MCP server would have helped here either way --
the fix path (read source, understand the shim's own two-phase
create/remove logic, replay its "create" half by hand) is exactly the
`discover -> read source -> call directly` loop the thesis is about,
just applied to a genuine bug instead of a genuine gap.

**Confirmed the actual async round trip, not just `{"ok": true}`:**
opened a real 7-line scratch `.py` file with three deliberate pyflakes
violations (`os` imported unused, `sys` imported unused, one undefined
name). By the time a *later*, separate `eval_python` call queried
`SublimeLinter.lint.persist.file_errors` -- well outside the tool call
that triggered the open/lint, and well past `eval_python`'s own 5s
main-thread timeout window -- all three real errors were already
present, each with correct line/column `Region` offsets and correct
messages, keyed by `linter: 'pyflakes'`. Screenshot-verified too: real
squiggly underlines on `os`, `sys`, and `undefined_variable_xyz`, a real
hover popup reading "pyflakes: 'os' imported but unused", and the status
bar showing `pyflakes(e:3)`. This is the actual answer to the axis
question: a background-thread lint worker's result is durable
process-level state (`persist.file_errors`, a plain dict on the 3.8
host), not something tied to the lifetime of the tool call that
triggered it -- so `discover -> run -> verify` survives async workers
the same way it survived every synchronous mechanism tested so far,
provided you query the package's real persisted state rather than
trying to synchronously await the tool call.

**Cleanup, verified not assumed:** closed the scratch file (not dirty,
plain `.close()`), deleted the scratch `.py` file, `pip uninstall
pyflakes`, `run_command(remove_packages, ["SublimeLinter-pyflakes",
"SublimeLinter"])` (plural again), then re-listed both `Packages/` and
`Installed Packages/` and confirmed byte-for-byte the exact pre-session
package set was restored.

verb is not a safe stand-in for the dedicated `install_package` tool --
their argument shapes differ (`package` vs `package_name`) and only one
of them is correct; prefer the purpose-built tool when one exists rather

**FALSE RETRACTION, then re-confirmed -- a methodology lesson about
console-capture completeness, not about the bug.** First did a
"clean-room retest" (verified zero SublimeLinter traces in `Packages/`,
`Installed Packages/`, and `installed_packages`, then reinstalled with
identical calls/timing) and initially wrote up "does not reproduce" from
`get_console(mode="captured")`, which showed no traceback. That
retraction was itself wrong: `mode="captured"` is documented as
non-invasive and incomplete ("only messages observed since capture
began") and had silently dropped the crash lines. Re-checked the same
run with `get_console(mode="auto")` (the complete `visible_windows`
capture) and the identical `ImportError` traceback was there all along.
**Ran the full clean-room cycle two more times (4 total from verified-
clean state), each time confirmed via the complete-capture console, not
the incomplete one: all 4 runs crashed identically.** This is a
genuine, deterministic bug, not a race -- and the earlier retraction is
itself now retracted.

**The real mechanism, now fully understood via the complete log:**
SublimeLinter's `__allo__.py` shim ("SublimeLinter-lift") drops a loose
`Packages/SublimeLinter-pyflakes/.python-version` lift file on fresh
install; the very next `reload_plugin` falls back to legacy Python 3.3
instead of the zip's own (correct) `.python-version` of `3.8`, and
`linter.py` dies with `ImportError: No module named 'SublimeLinter'`
every single time. But this is **self-healing**: Sublime's own crash
quarantine catches the repeatedly-failing plugin and auto-adds it to
`ignored_packages` (`"ignored packages updated to:
[\"SublimeLinter-pyflakes\", \"Vintage\"]"` in the log), then a moment
later un-ignores it again, and the *next* reload picks up the 3.8 host
correctly -- `persist.linter_classes` ends up with `'pyflakes'`
registered and linting genuinely works, which is exactly why a
"does it work in the end" check (my mistaken retraction) misses the
bug entirely: the visible symptom is a real traceback in the console on
every fresh install, self-corrected within a couple of seconds by ST's
own crash-recovery machinery, not a user-facing failure. **Filed
upstream:** https://github.com/SublimeLinter/SublimeLinter/issues/1993
-- found and cross-referenced a prior report (#1987, "Installation Fails
on Arch") that hit the identical traceback with a different linter
(cppcheck) on Linux a year earlier, closed by the reporter for an
unrelated reason without the crash itself ever being explained. Filing
required switching the GitHub MCP token from a fine-grained PAT (which
can't create issues on repos it doesn't own) to a classic PAT with
`public_repo` scope.

**New methodology lesson, the important one from this whole detour:**
`get_console(mode="captured")` is not a valid way to verify "no crash
occurred" -- it can silently drop lines and will falsely report a clean
run. Any "does this reproduce" check needs `mode="auto"` (or
`mode="visible"`), the complete capture, never the incomplete one. This
one bit the campaign's own "clean-room retry" discipline: the *retry
methodology* was right, but the *verification tool used inside the
retry* was wrong, producing a false-negative on top of what would have
otherwise been a correctly-confirmed bug.

MCP server to surface it. Filed upstream as

repo's only other open issue, #1, is an unrelated `searchengines`
problem), with the exact root-caused explanation and a suggested
one-line fix (add `:` to the `terminator` list, or compare with
`url.rstrip(':') == 'GOTOANCHOR'` instead of exact equality).

`installed_packages` list.

the thesis: the bug above was found *faster and more precisely* via
