# package-skill-generator random-sample test log

Started 2026-09-09. Goal: stress-test the "discover -> read source -> call
directly, no dedicated MCP needed" thesis against a broad, unbiased sample
of real installed Sublime Text packages, not just ones picked for being
interesting. A few random packages per day for a week.

Packages already tested before this log existed (do not re-pick):
- OpenFileOverSSH (AncientRoman/SublimeOpenFileOverSSH) -- 1/1 commands,
  100% coverage, skill verified end-to-end against a real SSH target.
- Debugger (SublimeText's Debugger package) -- ~40% coverage documented
  (mechanical action table + state/breakpoints/control), deep tools
  (variables/callstacks/evaluate) not investigated.
- LSP (via LSP-pyright) -- hover/definition/references/etc. bridge
  documented and verified; found a live bug in lsp-mcp's own can_handle()
  call during testing.

## Log format

Each entry: date, package name + repo, install method, coverage
assessment (X/Y real commands captured), whether a skill file was
generated and where, whether it was verified against a live action or
only read-verified, and any real gotcha/bug found. Be honest about
partial or failed cases -- this log exists to find where the thesis
breaks, not to pad a success count.

### Day 1 (2026-09-09): Notr

Repo: cepthomas/Notr (2.2MB, actively maintained, pushed 2026-08-03).
17 commands, 5 settings, 1744 lines across 3 source files (notr.py,
sbot_common.py, table.py). Picked specifically because the user pushed

being "astounded at the craftsmanship" -- this needed to be a real,
substantial package, not another trivial one.

**Result: thesis holds, but with a real, concrete exception found.**

  `sys.modules` and calling `_open_project()`/`_process_all_files()`
  directly, the same pattern used for Debugger and LSP -- worked
  perfectly. No dedicated MCP server was needed; `eval_python` alone
  handled the one case `run_command` couldn't.
- Verified end-to-end: opened the package's own shipped demo project
  (extracted from the .sublime-package zip, paths rewritten since it
  assumed a loose install), state initialized correctly, then the
  standard `notr_dump` command via plain `run_command` returned real,
  correct parsed content.
- Skill written: ~/.claude/skills/notr-control/SKILL.md.

### Day 1, second package (2026-09-09): Helium

Repo: SublimeText/Helium (6.5MB, actively maintained, pushed 2026-08-06).
"Let Sublime Text talk with Jupyter" -- vendors the entire real
`jupyter_client` library (kernel discovery, connection files, session
management) plus `traitlets` and `ipython_genutils` directly into the
plugin. By far the most structurally complex package looked at so far --
a real test of whether the thesis holds against genuine infrastructure,
not just a feature-rich but self-contained package like Notr.

**Result: could not be tested at all -- a different kind of finding.**

The plugin's own module failed to import entirely:
`ModuleNotFoundError: No module named 'zmq'`. Helium vendors the pure-
Python parts of the Jupyter client stack but not `pyzmq`, which needs a
compiled binary matching Sublime's embedded Python 3.8 build exactly --
not something that can be vendored as plain source, and not present in
this Sublime install. Confirmed via the real traceback from
`get_console()`, not guessed.

This is a genuine boundary case for the whole thesis, not a point for or
against it: when the underlying package can't even load, no control
technique applies -- not `run_command`, not `eval_python`, not a
dedicated MCP server either. The question "can you control this package
without a dedicated MCP" doesn't arise until the package actually works
in the first place. Did not attempt to install `pyzmq` to unblock this --
the user has been burned by Python environment installs before and asked
not to go there. Package fully uninstalled afterward (settings entry +
`.sublime-package` file removed directly, matching the debugger-mcp/
lsp-mcp removal method from earlier tonight) rather than left in a
broken, non-functional state.

Also hit a small, separate discovery mid-cleanup: Package Control's own
`remove_package` command does not accept `package` or `package_name` as
a kwarg when called via `run_command` (`TypeError: run() got an
unexpected keyword argument`) -- it's evidently UI-only (shows its own
picker) like several other commands found tonight. Worth remembering for
future cleanup: go straight to the settings-file + file-deletion method
instead of guessing at `run_command` args for it.

The user pushed back hard on leaving AssistantAI's silent failure as
"root cause not fully traced" -- correctly. They also pointed out

package's 5-file, ~60-field configuration surface represents, having

plugin worked correctly end-to-end; the entire defect is that its one

or an agent alike. Fully confirmed, not guessed -- both my scripted

identical, now fully-explained silence. Skill file updated with the
complete root cause and the real diagnostic command

**Process lesson, stated plainly because it's worth remembering**: I
stopped investigating one exception handler short of the real answer
and wrote up "root cause not fully traced" as if that were an acceptable

Twice tonight now (this, and the earlier LLM `sublime_llm_clear_chat`
overstatement) the user caught me settling for a plausible-sounding
account instead of the actual confirmed one. Push one level deeper before
calling an investigation done, especially when a concrete tool (like a
package's own diagnostic command) is available and unused.

## Package 10: FileBrowser (kaste/SublimeFileBrowser)

Richest command surface tested this run (50 commands). An
Emacs-dired-style file manager rendered as an editable text buffer.
Confirmed on the modern Python 3.8 plugin_host, so full `eval_python`
internals-reach applies.

Two real, confirmed findings:

1. **`assert` statements are silently no-ops in Sublime's plugin_host**
   -- it runs with `-O` (`__debug__ is False`, `sys.flags.optimize ==
   1`). `dired_create`'s `assert which in ('file', 'directory')` never
   fires; calling it with no `which` falls straight through to a
   `None.capitalize()` crash instead of a clean assertion error. This
   is a general finding about every package tested, not just this one
   -- any `assert`-based input validation in a Sublime package is not
   real validation in production.

2. **Input-panel views (from `window.show_input_panel`) are invisible
   to the normal view-discovery APIs** -- not in `window.views()`, not
   returned by `window.active_view()` (which kept returning unrelated
   views, including once the GhostShell "Claude" control tab itself),
   and not findable by scanning nearby view ids (they live in a
   separate low-id namespace, e.g. id `3`). The only reliable way found
   to get the real panel view was to monkeypatch
   `sublime.Window.show_input_panel` for one call to capture the id it
   returns, then drive that `View` directly (`insert`, then
   `dired_create_and_open`). Verified end-to-end: this created a real,
   empty file on disk at the target path, confirmed via a direct
   filesystem check afterward, not just trusting the command's `{"ok":
   true}` return.

Skill file: `~/.claude/skills/filebrowser-control/SKILL.md`. Uninstalled
after testing per the established pattern (settings entry removed,
`.sublime-package` file deleted).

**Takeaway**: this package needed the most investigative work of any
tested so far (three separate wrong assumptions before finding the real
input-panel view), but every technique that eventually worked was still
just "read the source, then use general `eval_python`/`sublime` API
tricks" -- no dedicated MCP server would have changed that discovery
cost, since the same input-panel-visibility gap exists at the raw
Sublime API level regardless of who's calling it.

10 packages fully tested and documented for day 1.

`New connection ... 21:44:41` / `Connection ... is closed. 21:44:54`

past this one package: **can `eval_python` hold a live socket open
across separate calls at all**, the way a real rmate session (or any
other TCP-backed control scheme) needs to stay open for the life of an
edit session? Confirmed yes, with a generic test unrelated to

call. This is the actual mechanism that would make a genuine rmate

than assumed from the narrower, already-corrected RemoteSubl test.

interpreter can dial in as the client, and hold the connection open

remaining candidates that could actually force a dedicated MCP are
narrower than "runs its own server" -- e.g. a native OS-modal dialog

### Isolated follow-up (2026-09-10): resolving the quick-panel `select` gap left open by SublimeZilla

Not a package test -- an isolated mechanism test, as the SublimeZilla entry
itself called for, using a throwaway `window.show_quick_panel` built
straight from `eval_python` (no third-party package involved) to get the
cleanest possible signal.

**Result: the gap is closed, and the answer is narrower than hoped.**

- `run_command("select")` does fire a live quick panel's `on_select`
  callback -- confirmed twice, cleanly: `on_select(0)` fired both times,
  matching the panel's default-highlighted item.
- Read `Default (Windows).sublime-keymap` directly (via
  `sublime.load_resource`, not guessed) for anything bound under an
  `overlay_has_focus` context that could move the highlighted item (the
  equivalent of arrow-key navigation before submitting) -- found nothing.
  Every `overlay_has_focus`-gated binding in the whole keymap is `select`
  itself (Enter) or a `goto`-overlay-specific extend/select variant; there
  is no keymap-reachable, and therefore no `run_command`-reachable, way to
  change *which* item is highlighted before calling `select`.
- **Conclusion**: quick-panel arrow-key navigation is native UI, not a
  Sublime command -- structurally unreachable via `run_command`, the same
  category of gap as ColorPicker's native `ChooseColorW` dialog, just a
  smaller one. `select` alone only ever accepts whatever is *already*
  highlighted (the default item, almost always index 0), never "item N."
  Confirmed authoritatively against Sublime's own official API reference
  (`sublimetext.com/docs/api_reference.html`), not just inferred from the
  keymap's silence: `show_quick_panel()`'s `selected_index` sets only the
  *initial* highlight at open time, and `on_select`/`on_highlight` are
  passive callbacks with no corresponding way to drive the highlight from
  script after the panel is already open -- the keymap search and the
  documented API agree exactly.
- This does **not** reopen the campaign's core finding, because the actual
  fix was already discovered and used earlier this campaign, just not
  named as the general answer to this specific question: the
  `show_quick_panel`-monkeypatch-and-call-the-real-callback-directly
  technique (first used for FileBrowser's input panel, reused successfully
  for BracketHighlighter's `swap_brackets` quick panel) bypasses UI
  navigation entirely and can select any index, not just the default. For
  SublimeZilla specifically, the earlier "inconclusive" `select` attempt
  should have used that technique instead, not `select`.

**Takeaway**: two genuinely different verbs were being conflated under one
question. "Submit whatever's highlighted" (`select`) and "choose a specific
item" (monkeypatch-and-call) are different mechanisms with different
reach -- `select` is not a general quick-panel driver, it's a narrow
accept-the-default action. `drive_input_panel`'s clean generalization to
other packages' input panels does not extend to quick panels, and building
a quick-panel equivalent of `drive_input_panel` would need to select the
monkeypatch approach, not try to extend `select` further.

`kylebebak/Requester`. Vendors the real `requests`/`urllib3`/`oauthlib`/

`computer-use`-style tool is the correct, and only, answer for this
specific narrow case, confirming the ColorPicker takeaway's prediction
rather than contradicting it.

### Retroactive correction (2026-09-10): a real Requester bug on Windows, found in the console dump, not the live test

Reading the full console after Requester's entry (triggered while
investigating an unrelated MarkdownPreview install) surfaced a genuine
crash from Requester's own history-writing code that the live test missed
at the time -- honestly logged after the fact rather than left buried in
a console dump nobody read closely:

```
FileExistsError: [WinError 183] Cannot create a file when that file
already exists: '...\Packages\User\Requester.history.json' ->
'...\Packages\User\Requester.history.json.bkp'
```

`core/__init__.py`'s `write_json_file` (called from `persist_requests`,
which every successful request triggers) does an atomic write via
temp-file-then-rename to a `.bkp` backup path. `os.rename()` on POSIX
silently overwrites an existing destination; on Windows it raises
`FileExistsError` instead -- a real, platform-specific bug, not a
one-off. It didn't visibly break the test (the response tab still
rendered correctly, since the exception is in the history-persistence
path, not the request/render path), which is exactly why it went
unnoticed until the console was read in full. Filed:
https://github.com/kylebebak/Requester/issues/41

**Takeaway, reinforcing an existing one**: this is the same lesson as
HypnotoadSVN's misdiagnosis and the WakaTime/PyTest silent-failure
findings -- a component can look like it worked from its visible output
alone while a real, confirmed exception fires in a parallel code path.
Reading the full console after a test, not just checking the one output
that mattered, keeps finding real bugs this campaign would otherwise
report as clean successes.

### Day 3 (2026-09-10): AutoFileName -- first package testing Sublime's autocomplete mechanism (on_query_completions)

`BoundInCode/AutoFileName`. Legacy Python 3.3 host (confirmed via console's
`reloading python 3.3 plugin AutoFileName.autofilename`). Introspection
surfaced no completion-related command at all -- expected, since
`on_query_completions` is an `EventListener` hook, not a command; the
package's actual trigger command, `afn_show_filenames`, is keymap-only,
the fourth instance of this pattern this campaign (after DocBlockr,
MarkdownPreview, and Requester's syntax file).

**Result: clean success confirming autocomplete IS fully reachable via
`run_command`, but only after three wrong turns, each a genuine
methodology lesson, not a package flaw.**

- First attempt: plain `run_command("auto_complete")` on a bare `<img
  src="` line with no typed prefix -- `is_auto_complete_visible()` false.
  Screenshot confirmed no popup, ruling out an API-reliability doubt.
- Read `get_cur_path()` directly: it returns an empty string unless a
  path separator (hardcoded `'/'`, checked directly -- not `os.sep`, so
  this is OS-independent, not a Windows-vs-POSIX issue) already appears
  before the cursor. A bare `<img src="s` has no completions to offer by
  design; this isn't a trigger character on its own, `/` is.
- Second attempt: `<img src="./` (no closing quote) -- still nothing.
  Reading `get_cur_path()` further showed it slices `[1:-1]` off the
  extracted scope's first line assuming a leading AND trailing quote;
  with no closing quote, that slice cuts a real path character instead
  of a closing quote, corrupting the parse. This turned out to be a
  synthetic-test artifact (real typing always has a matching closing
  quote already, from HTML's own auto-pair-insertion), not a bug.
- Third attempt, matching realistic usage exactly (`<img src="./">`,
  cursor between the `/` and the closing `"`): real popup appeared,
  confirmed both visually (screenshot: a real completion list showing
  `C:/`, `D:/` -- genuine drive letters on this machine, mixed with
  ordinary word-completions from an unrelated snippet package) and via
  `is_auto_complete_visible()` returning `True` this time -- settling
  the earlier doubt about the API's reliability: it was accurate both
  times, the popup genuinely wasn't there for the first two attempts.
  (Showed drive roots rather than the test directory's actual contents --
  likely an artifact of building the test buffer via instant
  select-all+replace rather than incremental typing, which the plugin
  may partly rely on for directory-tracking state; not chased further.)

No dedicated MCP server needed -- `run_command` reaches
`on_query_completions`-driven completions exactly like any other command,
once the plugin's own real trigger conditions (the actual keymap command,
a matched trigger character, a syntactically complete context) are met.

**Takeaway**: this campaign's methodology paid for itself three times in
one package -- read the source before assuming a mechanism is unreachable
(it wasn't), don't trust a synthetic test input that a real user's editor
would never actually produce (auto-paired quotes), and re-verify a
boolean state check with a screenshot when its result contradicts
expectation rather than trusting either blindly.
