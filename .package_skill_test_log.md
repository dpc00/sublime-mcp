# package-skill-generator popularity-sample test log

Started 2026-09-09. Goal: determine where there is a serious need for
an MCP other than the base sublime-mcp -- i.e. which real, popular
Sublime Text packages genuinely require their own dedicated
integration (the way Debugger and LSP got real
`debugger-control`/`lsp-control` skills), versus ones sublime-mcp's
generic "discover -> read source -> call directly" already covers
completely. A package nobody uses isn't worth building anything
dedicated for regardless of the answer, so candidates are selected by
real install-count ranking from `packagecontrol.io/browse/popular.json`,
not by unfiltered random draw from the full package corpus.

**Rolled back 2026-09-14**: entries for packages 24+ (HypnotoadSVN
onward) were selected by pure random sampling against a 4442-entry
`clone_list.tsv` corpus instead of the install-count criteria above --
that drift produced a long run of low-usage, unmaintained "dog"
packages irrelevant to the actual question. Those entries were deleted,
not archived. Resuming from package 23 (AdvancedNewFile), next pick by
real packagecontrol.io popularity rank.

**Standing methodology rule (added day 5, applies retroactively to every
entry below that claims "no error occurred"): `get_console(mode="captured")`
is NOT valid for verifying the absence of a crash.** It is explicitly
non-invasive and incomplete -- it can silently drop lines, including
tracebacks, and will falsely report a clean run. It produced exactly this
false negative on SublimeLinter-pyflakes (package #37): a run that had
actually crashed 4/4 times looked crash-free under `mode="captured"` and
only showed the real traceback under `mode="auto"`/`"visible"` (the
complete capture). Any "did this actually work / did this actually
crash" check must use the complete capture, never the incomplete one.
Earlier entries in this log that checked console output for absence of
errors were not necessarily using the complete capture and have not been
retroactively re-verified against this rule -- treat any of them as
provisional if the distinction matters for a specific decision.

**Second standing methodology rule (added closing this campaign, from
the EditorConfig #39 trim-whitespace false finding): an edit-then-save
round trip must verify the edit landed where intended before trusting
the save result.** Inserting a test marker *after* the region actually
being tested (e.g. after trailing whitespace, when testing whether
trailing whitespace gets trimmed) silently changes what the test is
measuring -- the marker makes prior content interior, not trailing, so
there is nothing left for the feature under test to act on. This
produced a real false "bug" report in the same session it was found.
Print/verify the actual buffer content immediately after making a test
edit, before saving and checking the result.

Packages already tested before this log existed (do not re-pick):
- OpenFileOverSSH (AncientRoman/SublimeOpenFileOverSSH) -- 1/1 commands,
  100% coverage, skill verified end-to-end against a real SSH target.
- Debugger (SublimeText's Debugger package) -- ~40% coverage documented
  (mechanical action table + state/breakpoints/control), deep tools
  (variables/callstacks/evaluate) not investigated.
- LSP (via LSP-pyright) -- hover/definition/references/etc. bridge
  documented and verified; found a live bug in lsp-mcp's own can_handle()
  call during testing.

## Log format

Each entry: date, package name + repo, install method, coverage
assessment (X/Y real commands captured), whether a skill file was
generated and where, whether it was verified against a live action or
only read-verified, and any real gotcha/bug found. Be honest about
partial or failed cases -- this log exists to find where the thesis
breaks, not to pad a success count.

Repo: SublimeText/Helium (6.5MB, actively maintained, pushed 2026-08-06).
"Let Sublime Text talk with Jupyter" -- vendors the entire real
`jupyter_client` library (kernel discovery, connection files, session

**Result: could not be tested at all -- a different kind of finding.**

`get_console()`, not guessed.

This is a genuine boundary case for the whole thesis, not a point for or
against it: when the underlying package can't even load, no control
technique applies -- not `run_command`, not `eval_python`, not a
dedicated MCP server either. The question "can you control this package
without a dedicated MCP" doesn't arise until the package actually works
in the first place. Did not attempt to install `pyzmq` to unblock this --
the user has been burned by Python environment installs before and asked
not to go there. Package fully uninstalled afterward (settings entry +
`.sublime-package` file removed directly, matching the debugger-mcp/
lsp-mcp removal method from earlier tonight) rather than left in a
broken, non-functional state.

Also hit a small, separate discovery mid-cleanup: Package Control's own
`remove_package` command does not accept `package` or `package_name` as
a kwarg when called via `run_command` (`TypeError: run() got an

picker) like several other commands found tonight. Worth remembering for
future cleanup: go straight to the settings-file + file-deletion method
instead of guessing at `run_command` args for it.

## Package 10: FileBrowser (kaste/SublimeFileBrowser)

Richest command surface tested this run (50 commands). An
Emacs-dired-style file manager rendered as an editable text buffer.
Confirmed on the modern Python 3.8 plugin_host, so full `eval_python`
internals-reach applies.

Two real, confirmed findings:

1. **`assert` statements are silently no-ops in Sublime's plugin_host**
   -- it runs with `-O` (`__debug__ is False`, `sys.flags.optimize ==
   1`). `dired_create`'s `assert which in ('file', 'directory')` never
   fires; calling it with no `which` falls straight through to a
   `None.capitalize()` crash instead of a clean assertion error. This
   is a general finding about every package tested, not just this one
   -- any `assert`-based input validation in a Sublime package is not
   real validation in production.

2. **Input-panel views (from `window.show_input_panel`) are invisible
   to the normal view-discovery APIs** -- not in `window.views()`, not
   returned by `window.active_view()` (which kept returning unrelated
   views, including once the GhostShell "Claude" control tab itself),
   and not findable by scanning nearby view ids (they live in a
   separate low-id namespace, e.g. id `3`). The only reliable way found
   to get the real panel view was to monkeypatch
   `sublime.Window.show_input_panel` for one call to capture the id it
   returns, then drive that `View` directly (`insert`, then
   `dired_create_and_open`). Verified end-to-end: this created a real,
   empty file on disk at the target path, confirmed via a direct
   filesystem check afterward, not just trusting the command's `{"ok":
   true}` return.

Skill file: `~/.claude/skills/filebrowser-control/SKILL.md`. Uninstalled
after testing per the established pattern (settings entry removed,
`.sublime-package` file deleted).

**Takeaway**: this package needed the most investigative work of any
tested so far (three separate wrong assumptions before finding the real
input-panel view), but every technique that eventually worked was still
just "read the source, then use general `eval_python`/`sublime` API
tricks" -- no dedicated MCP server would have changed that discovery
cost, since the same input-panel-visibility gap exists at the raw
Sublime API level regardless of who's calling it.

### Day 2 (2026-09-09): RemoteSubl -- deliberately picked to attack the thesis, not just sample it

`randy3k`'s active fork of `henrikpersson/rsub` (the rmate protocol for
Sublime). Picked specifically because its architecture is the inverse of
every package tested so far: `plugin_loaded()` starts a raw
`socketserver.ThreadingTCPServer` on `localhost:52698` and *waits for an

normally piped in over an SSH `-R` tunnel from a remote box). Every
other package in this campaign exposes behavior the agent calls *into*
via `run_command`/`eval_python`; this one exposes nothing callable at
all -- `get_package_mcp_info` surfaced exactly one command
(`edit_settings`, boilerplate). If any package was going to need a real

one.

caught and corrected before closing this entry, same discipline as the
LLM/AssistantAI corrections above.** `eval_python` is not limited to
Sublime's own API -- it's a full embedded Python interpreter, so it can
just `import socket` and *be* the external rmate client itself, in the
same process, no separate process or server required.

- Opened a raw `socket.create_connection(('localhost', 52698))`,
  received the real banner (`Sublime Text 3 (remote_subl plugin)`).
- Sent a real `open` / `display-name` / `real-path` / `token` / `data: N`
  frame per the rmate wire protocol (reverse-engineered directly from
  `remote_subl.py`'s `Session.parse_input`, not from external docs).
- Confirmed a real file materialized with the exact sent content, read
  back via `view.substr()` on the actual opened view.

Initially logged this as a "full real protocol round trip," which was
wrong: that first test only exercised the inbound half (client -> open
file). The socket lived in one `eval_python` call's locals, which don't
survive to the next call, so it was already dead by the time the file's
view was closed -- confirmed directly in the ST console:
`New connection ... 21:44:41` / `Connection ... is closed. 21:44:54`
(closed on its own, ~13s later, when the dead socket was garbage
collected) / `Error closing rmate_test.txt in testhost. 21:45:00` (the
`on_close` handler's `file.close()` tried `session.send("close")` on
the already-closed socket, raised, and skipped its own `os.unlink`/

afterward, cleaned up manually). No `CONNECTION_LOST` dialog text
appeared in the console for the natural disconnect, and every
subsequent call kept responding promptly, so the background handler
thread's `cleanup()` (which does call a real `sublime.message_dialog`
on disconnect by default) did not visibly wedge the main thread here --
but the earlier claim of a clean full round trip was still not earned.

Went back and settled the actual crux directly, since it generalizes
past this one package: **can `eval_python` hold a live socket open
across separate calls at all**, the way a real rmate session (or any
other TCP-backed control scheme) needs to stay open for the life of an
edit session? Confirmed yes, with a generic test unrelated to
RemoteSubl -- stashed a live loopback socket pair as an attribute on
the already-imported `sublime` module (a persistent object across calls
in the same long-lived plugin_host process) in one `eval_python` call,
then sent/received real bytes both directions from a second, separate
call. This is the actual mechanism that would make a genuine rmate
save-back round trip (or a hypothetical write-your-own-rmate-client
MCP tool) work via plain `eval_python` -- confirmed generically rather
than assumed from the narrower, already-corrected RemoteSubl test.

No dedicated MCP server needed. Uninstalled after testing via the
`PackageTaskRunner.remove_packages` internals-reach method, verified
against `list_packages()` and against nothing still listening on 52698.

**Takeaway, and the actual point of this entry**: "genuinely needs a
dedicated MCP" would require a client protocol `eval_python` truly
cannot speak -- not just an unusual *direction* of control, and not
just a connection that has to outlive a single tool call (confirmed
separately that it can, via the persistent-module-attribute pattern).
A listen-and-wait TCP server is not that: `eval_python`'s Python
interpreter can dial in as the client, and hold the connection open
across calls, just as easily as it can call a Sublime command. The
remaining candidates that could actually force a dedicated MCP are
narrower than "runs its own server" -- e.g. a native OS-modal dialog
with no scriptable handle (ColorPicker's `ChooseColorW`, already found
and documented above) or a binary/proprietary wire format `eval_python`
has no library for. Both would need testing on their own merits, not
inferred from "it manages a server."

### 2026-09-14 (later still): live install-and-exercise bug hunt, in progress

Different task from everything above: the user asked to actually install
and run real packages live, one at a time, looking for genuine bugs worth
filing -- not just reading source. Target list: the ~40 substantive real
plugins out of the 182-package shortlist (the trivial one-file config
wrappers and non-plugins were already excluded). Only writing something
up here if it's a real, reproducible bug with real before/after evidence.

**A File Icon -- real bug found, live, by accident during normal use.**
What happened: the package's "revert" command (the only command it has)
was run, then shortly after, the package was removed the normal way. A
few seconds later, Sublime Text's own console showed a real crash
message on its own, with a full error trace, coming from code inside A
File Icon that had no idea the package had just been removed:

```
Traceback (most recent call last):
  File ".../A File Icon.sublime-package/plugin.py", line 35, in remove_overlay
  File ".../A File Icon.sublime-package/core/settings.py", line 24, in add_listener
  File "...\sublime.py", line 1199, in load_resource
    raise FileNotFoundError(f'resource "{name}" not found')
FileNotFoundError: resource "Packages/A File Icon/A File Icon.sublime-settings" not found
```

In plain terms: when you run A File Icon's "revert" command, it doesn't
clean up right away -- it schedules some follow-up cleanup work to
happen a fraction of a second later, in the background. Part of that
follow-up work is: "go re-read my own settings file." That's fine if the
package is still there when the follow-up work actually runs. But if the
package gets removed (by a normal uninstall, or by Package Control
upgrading it to a new version, which also removes-then-reinstalls) in
that same short window, the follow-up work tries to read a settings file
that no longer exists, and the whole thing crashes with an ugly error in
the console instead of failing quietly. This is a real, timing-dependent
bug in the package's own cleanup code, not anything about how it was
invoked -- and it's realistic to hit by accident, exactly as it was hit
here: run the "revert" command, then remove or upgrade the package
shortly after. Repro steps for whoever files this: install "A File
Icon," run its "AFI: Revert filetype changes" command from the command
palette, then immediately remove or upgrade the package before a couple
of seconds pass -- the console shows the exact traceback above. The fix
on the package's end would be wrapping that follow-up settings reload in
a try/except (the same pattern the package already uses in a couple of
other places) instead of leaving it bare.

**ApplySyntax -- a second, different bug read from the source and set up
to test live, but the live confirmation didn't finish (see blocker
below).** Reading the package's own code found a real inconsistency: it
has a setting called "reraise_exceptions" whose whole documented purpose
is "keep errors from showing up in the console unless you turn this on."
The package actually honors that setting in two of its three ways of
matching a file to a syntax (its "glob pattern" matching and its
"custom function" matching both correctly hide their errors by default).
But its third way of matching -- plain regular-expression rules, like
"if the file's first line looks like this pattern, use this syntax" --
has no such protection at all. A broken regular expression in a user's
own syntax rule (an easy mistake -- unbalanced brackets/parentheses is a
one-character typo) will throw a real, uncaught error every single time
a file is opened or saved, regardless of the "reraise_exceptions"
setting, which is supposed to prevent exactly that. This was set up for
a live test (installed the package, wrote a syntax rule with a
deliberately broken regular expression, created a test file to open) but
the actual live confirmation -- watching the real error happen when the
file opens -- did not complete before the environment blocker below hit,
so this is not yet confirmed the same way the A File Icon bug is. Worth
someone re-running: install ApplySyntax, add a rule like `{"name": "x",
"syntax": "Packages/Text/Plain text.tmLanguage", "rules": [{"first_line":
"(unclosed["}]}` to the "syntaxes" list in ApplySyntax's User settings,
then open any real file and check the console.

**Blocker hit partway through package 2 of ~40: the shared Sublime
instance's main thread got stuck.** This has nothing to do with either
package above -- while working through ApplySyntax, Sublime Text's main
thread stopped responding to anything (every kind of call started timing
out: running commands, running Python, even just listing installed

sessions/terminal tabs sharing one live Sublime Text process can starve

**Bracketeer -- clean, no bug.** Read its bracket-jump command

**AutoSetSyntax -- real, confirmed bug: the package can fail to load at
all, for every single feature, not just the one it's trying to work
around.** This one wasn't even part of the planned edge-case test --
installing the package fresh and opening one ordinary file (an empty
text file) was enough to trigger it immediately, live, with a full
error trace:

```
File ".../AutoSetSyntax.sublime-package/boot.py", line 32, in <module>
File ".../AutoSetSyntax.sublime-package/boot.py", line 23, in bypass_pydantic_version_check
File "./python3.8/pathlib.py", line 1229, in read_bytes
FileNotFoundError: [Errno 2] No such file or directory:
  '...\\Lib\\python38\\pydantic\\version.py'
```

In plain terms: AutoSetSyntax ships a small workaround (its own code
comment links to the exact GitHub issue it's patching) for a known
conflict with a library called "pydantic" that Package Control itself
carries internally. The workaround's very first move, before anything
else in the package even starts, is to open and rewrite one specific
file inside Package Control's own internal folder. That file genuinely
wasn't there in this environment when AutoSetSyntax was installed
(confirmed directly: Package Control's internal library folder had no
"pydantic" folder in it at all at that moment). The workaround has no
fallback for that -- it only handles "Package Control isn't installed at
all" (that case is wrapped safely), not "Package Control is installed
but doesn't have this particular internal file yet." Because this code
runs immediately when the package's main file loads, and nothing catches
the error, the *entire* package fails to load -- not just the specific
pydantic-related feature, everything, syntax detection included, the
thing the package is actually for. Confirmed reproducible: happened
identically and immediately on a fresh install with no special setup.
Repro for whoever files this: install AutoSetSyntax fresh in an
environment where Package Control's own bundled "pydantic" library
folder isn't present yet, and watch the console right after install --
the traceback above appears immediately, before the package does
anything else. The fix on the package's end is straightforward: wrap
that file read/write in a try/except the same way the "is Package
Control even installed" check already is, so a missing file just skips
the workaround instead of taking down the whole package.

**Methodology note, applies going forward:** installing a package
through this session's install tool does not automatically finish
resolving its non-package Python library dependencies (things like
"pydantic" that several packages share, installed separately from the
package itself) -- that needs Package Control's own "Satisfy Libraries"
step run explicitly afterward. Found this the hard way on the very next
package below, which looked broken because of the missing library, not
because of anything in the package's own code. Will run "Satisfy
Libraries" after every install from here on to avoid false alarms.

**BootstrapAutocomplete -- real, confirmed bug (after correctly ruling
out the dependency red herring above).** Its autocomplete list is
chosen by a "versions" setting (which Bootstrap version(s) to offer
completions for). Give it a version string that doesn't match any of
the Bootstrap versions the package actually ships data for -- a typo is
all it takes, e.g. "5" typed as "5x" -- and every single autocomplete
attempt in a matching file throws a real, uncaught error instead of
just not offering suggestions:

```
File ".../BootstrapAutocomplete.sublime-package/plugin/completion.py", line 15, in load_db
    return DbModel.model_validate_json(sublime.load_binary_resource(...))
FileNotFoundError: resource "Packages\BootstrapAutocomplete\db\not-a-real-version.json" not found
```

Confirmed live and directly: set "versions" to a made-up value, called

guessed, watched it happen. Because of how the lookup function is
cached internally, this doesn't just happen once -- it happens on every
single autocomplete request for as long as the bad setting is in place,

version file" case in its version-loading function and either ignore
that version or show a clear one-time settings warning, instead of
letting the raw file-not-found error escape on every keystroke.

**SSH Config -- real, confirmed bug: customizing just one of its four
file paths in settings silently breaks the other three.** The package
ships default locations for four files (SSH config, SSHD config, known
hosts, authorized keys) as one settings block per operating system. If
someone wants to override just one of those four paths -- a completely
natural thing to try, since it's one JSON object -- Sublime Text's own
settings system doesn't merge nested objects, it replaces the whole
block. The user ends up with a settings block containing only the one
path they meant to change, and the other three "Open X" commands break
immediately:

```
File ".../SSH Config.sublime-package/main.py", line 17, in get_file_location
    return expandvars(setting[identifier])
KeyError: 'sshd_config'
```

Confirmed live with the real installed code: set a settings override
that customizes only the Windows SSH-config path (leaving the other
three keys out, exactly as someone would if they only meant to change
one), then asked the package for the SSHD config location the same way
its own "Open SSHD Config File" command does -- got the exact crash
above. Repro for whoever files this: in SSH Config's user settings, set
`"default_file_locations"` to an object containing only one platform
and only one file key (e.g. just `windows.ssh_config`), then run any of
the other three "Open ... File" commands -- the traceback above appears
immediately. The fix on the package's end: merge the user's override
into the shipped defaults key-by-key instead of trusting Sublime's
settings system to do it, or read each file key with a safe fallback
instead of direct indexing.
