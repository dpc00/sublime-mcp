Root cause of a 2026-09-15 session death, reconstructed from `agent_broker.log`, the raw asciinema recording of the dying session's own screen (captured text that never reached the Claude Code `.jsonl` transcript because the process died mid-write), and finally the actual `sublime_mcp.py`/`ai_terminal.py` source.

**What happened:** after live-verifying a new `ai_terminal_queue_input_to` command using a disposable "Bash" test tab alongside the coordinating session's own tab, I said "Cleaning up the disposable test tab" and called sublime-mcp's `close_file` tool with no `path` argument that actually resolved to the Bash tab. **The real bug:** `close_file` (`sublime_mcp.py`'s `_close_file`, pre-fix) can only match a real on-disk `path` via `w.find_open_file(path)`; ai_terminal tabs have no path at all (`"path": null` in every `get_sheets` result), so there was never a way to target the Bash tab by path. When the given/absent path didn't resolve, the code silently fell back to `w.active_view()` — and my immediately-prior action had been `focus_sheet index:0` (refocusing my own tab, to test targeting-while-unfocused), so the active view was my own tab. `close_file` closed it, calling `v.close()` directly.

**Why that actually killed the process (corrects an earlier wrong theory in this file):** an earlier version of this memory claimed ai_terminal tab-close is "intentionally wired to kill the child process outright, no orphan by design." **That was wrong** — checked directly against current `ai_terminal.py` source: `AiTerminalViewListener.on_close` (fires on every close path, any method) always calls `term.kill()`, and `_BrokerPty.kill()`'s own docstring is explicit: *"Disconnect this client only. The broker and its agent process keep running -- that's the point of a detachable session."* Real termination is a separate, deliberately opt-in method, `explicit_kill()` (sends `KILL\n` over the control pipe). This detach-not-kill design was shipped 2026-09-09 specifically to fix the mouse-X close problem (see ghostshell_mouse_tabclose_bug_1922 (note not found) in GhostShell's memory) and was already in place during this incident. So `v.close()` should only have detached, not killed — yet `agent_broker.log` shows the underlying `claude.exe` (pid 13448) genuinely exited (`child process exited ... exit_code=unknown (GetLastError 6)`), and the broker then stopped because the child was gone. The most likely explanation: the bare Claude Code CLI (unlike `omp`, which is built to survive detach/reattach — confirmed working earlier the same day) does not itself tolerate losing its PTY connection and exits on its own when detached, even though `ai_terminal.py`'s own close path never asked it to. This means "close only detaches" is not by itself a sufficient safety net for this kind of session even when it works exactly as designed.

**`view.close()` also bypasses window-command interception entirely** — the same class of gap as Sublime's mouse-X tab close (`sublimehq/sublime_text#1922`, confirmed via GhostShell's own investigation): `on_window_command`-based hooks never see a direct API call. So even GhostShell's pre-existing `AiTerminalTabCloseInterceptor` confirmation dialog (at the time, gated to profiles with a configured `tab_close_input`) could never have caught this regardless of gating.

**Fix landed 2026-09-15, in two rounds** (both sides, tested via `pytest`, live-verified via `diagnostics`/`get_console_log` after each reload):

1. `sublime_mcp.py`'s `_close_file` now routes through `window.run_command("close_file")` / `("close_by_index", {...})` instead of calling `v.close()` directly, specifically so any host-side close-confirmation hook gets a chance to run. This part didn't change in round two.
2. Round one: `ai_terminal.py`'s `AiTerminalTabCloseInterceptor.on_window_command` asked a plain yes/no (or 3-way) `sublime.*_dialog` before letting any ai_terminal tab close. Live-tested by the user immediately, and the native OS-modal dialog turned out to have its own real problem on Windows: it could lose focus and hide behind other windows while blocking the entire app with zero in-app cue, which caused confused clicking and orphaned two tabs (both recovered fine).
3. **Round two (current):** dropped the dialog approach entirely. `on_window_command` now blocks every native window-close command outright for any ai_terminal tab, unconditionally, no dialog at all -- `close_file`'s `window.run_command` call from step 1 now just gets refused with a status-bar message. Ending or detaching a session moved to a new in-tab "Tab Close ▼" toolbar reveal panel (fully within GhostShell's own phantom UI, can't hide behind another window) -- see GhostShell memory `feedback-dont-repropose-close-confirmation` for the full history.

**This closes the gap for real window-command closes (Ctrl+W, palette, menu, and sublime-mcp's `close_file`) but NOT for a future caller that still calls `view.close()`/`sheet.close()` directly** — that bypass is structural, not something either file can fully close from inside itself (mouse-X tab-close is the other permanently-uncatchable case, but it only ever detaches, never kills, which is the safe default).

**How to apply:** prefer letting the user close ai_terminal tabs themselves over calling `close_file` on one. As of round two, calling `close_file` on an ai_terminal tab now just does nothing (blocked, status message only) rather than either succeeding destructively or popping a dialog -- so it's safe to call by accident, but still useless for actually closing one; don't expect it to work and don't retry it hoping a confirmation will appear. Read this memory (and GhostShell's `feedback-dont-repropose-close-confirmation`) before making further changes to `close_file` or `ai_terminal.py`'s tab-close handling.
