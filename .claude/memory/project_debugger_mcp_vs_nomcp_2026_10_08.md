**Question (Donald):** does an AI agent need a separate per-package MCP (the audit began to answer this), or do the generic sublime-mcp tools do? Test: drive Sublime's Debugger package on the same task both ways. Earlier I glossed over Debugger (called its palettes untestable); Donald pointed to the history: a full `debugger-mcp` (removed in 435cf12, 2026-09-08; 79 tool definitions in the source, he remembers about 75, its guide said 104), a `sublime-debugger` skill, GhostShell-debug test projects, and an installed debugpy adapter in his main Sublime's Package Storage. See [[audit-exhausted-and-reload-hang-2026-10-08]].

**Task, both arms:** open the debugger, breakpoint on line 2 of a small sample.py, start with a global configuration, stop at the breakpoint, read call stack and variables, evaluate `a + b`, step over, continue, stop. Portable 4215 (Python 3.14 host), Debugger 0.12.1, debugpy copied from the main Sublime's Package Storage (30 MB, local copy, read-only), config in the portable's `User\Debugger.sublime-settings` (`global_debugger_configurations`, with an explicit "python" because the Windows Store python3 stub made the first run end at once).

**NO-MCP (generic tools only, no eval_python): 220 s, about 15 top-level calls, completed except evaluate.** `run_command debugger {action: start, configuration: "Sample"}` starts a session with no palette (my first attempt passed no configuration, hence the palette). Every `run_command` returns ok whatever happened. `open_file` returns before the file loads (my cursor move hit an empty buffer, breakpoint landed on line 1). State (Stopped: breakpoint, call stack add:2 / module:7, locals a=0 b=10) was readable only from screenshots; no text tool exposes the Debugger panes, the accessibility tree shows only window chrome, a background click on the Callstack tab did nothing, after a step the UI shows the Console tab so the variables were not readable. Evaluate / watch / console input need a list-input palette or keyboard input: not possible.

**MCP (old debugger-mcp restored into the portable, called through its HTTP bridge one tool per request): 188 s elapsed, did not complete.** `debugger_control start` fails with "There is no current event loop in thread ... process_request_thread" (async called from the HTTP thread; Python 3.14). Passthrough `debugger_start` starts the session (configuration_name ignored, uses the selected one). `debugger_toggle_breakpoint` says "Toggled breakpoint on line 2" but the package's own `debugger_get_breakpoints` shows none; `debugger_set_breakpoints_for_file` says "No active debug session." What works: `debugger_get_state` returns exact structured state (is_paused, thread MainThread, frame add, file, line 2) and `debugger_get_breakpoints` reads correctly once the breakpoint was set by the generic route. Every DAP reader (callstack, variables, evaluate) fails with the same event-loop error.

**Reading:** on today's stack the generic route was more reliable for control and the old MCP only wins on the structured state read; the MCP's DAP tools are broken by drift (Debugger 0.12 / Python 3.14 / build 4215 against a package written for 4200 / Python 3.8 / Debugger ~0.11). That drift is itself the finding for the per-package-MCP side (maintenance cost); the generic side's weakness is that it has no structured state or evaluate for packages whose UI is phantoms and list-input palettes.

**Caveats / not done:** one run per arm; my own latency is in both times; the MCP arm used its HTTP bridge, not the MCP transport in Claude Code (a new server needs a reconnect, avoided to protect the session). NOT run: the MCP on its native stack (portable 4200, Python 3.8 host) to separate "the idea" from "drift"; a third arm with the debugger-control skill (eval_python reading the Debugger's own objects), which the audit rules forbid but which would give structured state; the plugin-debugging case (the 'sublime' adapter, isolated Sublime window) that the GhostShell sessions came close to. Left installed in portable 4215 for a rerun: Debugger, debugger-mcp (ports 9505/9515), Debugger.sublime-settings, sample.py under the session scratchpad, debugpy under Data\Package Storage.
