Donald told me (2026-09-29): WSL is installed on this machine and has its own Sublime Text install, deliberately not updated. It did run sublime-mcp at one point (with its own ports, not 9510/9512/9520/9522). The install has OLD versions of the MCPs and packages, so it is not a clean or current baseline.

**Why it matters:** it is a Linux ST, so it could test Linux-only packages the Windows rig cannot run (e.g. Devhelp #696, whose GNOME app is Linux-only; other `platforms: linux` packages, shell/`/usr/bin` path assumptions). It is also an older ST build, so results there say nothing about 4215.

**How to apply:** don't assume it is running or that its ports are known; ask or check before using it. Treat its package/MCP versions as stale (may need updating or a fresh sublime-mcp copy before trusting results). Never mix its tools up with `mcp__sublime-mcp` (real ST 4200) or `mcp__sublime-mcp-portable` (portable 4215) -- verify the target instance first, same as [[feedback_mcp_disconnect_notify_dont_bypass]]. Related rig: [[reference_portable_st_4215]].

**Use it for command-line checks today (2026-09-29, Donald reminded me "there is wsl"):** distro `Ubuntu` (WSL 2, starts on demand, gcc 15.2, LANG=C.UTF-8). No Sublime needed: `wsl -e bash -c '...'` runs Linux CLI tools against files under `/mnt/c/...`. Used it to test gcc column behaviour on Linux for the SublimeLinter-gcc issue. Before saying a tool behaviour is "not tested on Linux", try WSL first.

**WSLg BLACK WINDOW / KEYBOARD FREEZE: ROOT CAUSE FOUND 2026-09-29 (Donald: "something runs before WSL... it won't work right").** The computer-use-mcp helpers (`computer-use-mcp.exe`, its node.exe + cmd.exe parents, and `CopilotComputerUse.exe`, restarted at every `/mcp` reconnect) start BEFORE WSL's `msrdc.exe`. With them running, WSLg windows render solid black with a "[WARN:COPY MODE]" title prefix, and the keyboard froze once (that tool hooks keyboard input to detect the "physical Escape key"; it also produces the false Escape stops). ORDER RULE: start WSL / WSL-ST first, computer-use only after; never call computer-use on msrdc windows. Untested: whether reconnecting computer-use AFTER the window is up breaks it again. Scripts in the scratchpad: order_test.ps1, wsl_launch_st_sw.sh, msrdc_windows.py, restore_wsl_window.py. Verify with mcp__screenshot__screenshot_window (works on all windows), not with Windows' own minimized/visible flags.
